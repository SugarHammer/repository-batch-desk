# Gitee README 批量修改工具设计

- 日期：2026-11-01
- 状态：设计已获用户确认，等待书面审阅
- 第一版平台：Gitee
- 后续扩展：GitHub、GitCode

## 1. 背景与目标

用户在多个开源平台维护数十个仓库，经常需要对多个 `README.md` 做相同修改。逐仓库打开网页、编辑并保存，重复且耗时。

第一版提供一个 Windows 本地图形工具，让用户能够：

1. 加载并勾选 Gitee 仓库。
2. 输入固定旧内容和新内容。
3. 在线读取选中仓库默认分支根目录的 `README.md`。
4. 查看每个仓库的替换结果和前后差异。
5. 确认后直接提交到各仓库默认分支。
6. 查看每个仓库的成功、跳过或失败结果，并重试可恢复失败。

工具不克隆仓库，不经过第三方服务器，未明确确认前不产生远端修改。

## 2. 第一版范围

### 包含

- 本地图形界面。
- Gitee 私人访问令牌认证。
- 分页加载授权用户可访问的仓库。
- 手动勾选仓库。
- 对根目录 `README.md` 进行区分大小写的固定文字替换。
- 支持单行、多行和删除内容（新内容为空）。
- 替换每个文件中的全部匹配项。
- 逐仓库差异预览、匹配次数和状态展示。
- 使用统一提交说明直接提交默认分支。
- 基于文件 SHA 的并发冲突保护。
- 逐仓库结果、提交链接和本地任务报告。
- 可恢复失败的单仓库重试。

### 不包含

- GitHub、GitCode 的实际接入，只预留平台适配接口。
- 正则表达式、章节级修改、统一插入和整文件覆盖。
- 自动创建缺失的 `README.md`。
- 修改其他路径、其他文件或非默认分支。
- 新建分支、Pull Request 或自动合并。
- 全选仓库的一键默认操作、定时任务、账号体系和云端同步。
- 批量回滚已经成功的提交。

## 3. 总体架构

工具由本地界面、任务协调器、替换核心、平台适配器、凭据存储和任务报告组成。界面与应用服务仅监听 `127.0.0.1`，不部署到互联网。

### 3.1 本地图形界面

启动本地应用后打开操作页面，负责：

- 接收令牌和“是否记住令牌”的选择。
- 展示、筛选和勾选仓库。
- 接收旧内容、新内容和提交说明。
- 请求生成预览，展示逐仓库差异。
- 在提交前展示仓库数和替换总数，并要求再次确认。
- 展示执行进度、提交链接、错误和重试入口。

筛选只影响界面显示，不会自动选中或取消选中仓库。仓库选择、替换规则或提交说明发生变化后，旧预览立即失效。

### 3.2 任务协调器

任务协调器负责预览和提交两个独立阶段：

- 校验输入和任务状态。
- 为每个选中仓库创建独立任务项。
- 限制并发数，默认最多同时处理三个仓库，避免触发接口限流。
- 汇总结果，但不让单个仓库失败中断整批任务。
- 只允许提交状态为“待提交”且预览仍有效的任务项。
- 对网络异常和限流执行有限重试，对权限、内容及 SHA 冲突不盲目重试。

### 3.3 替换核心

替换核心为不依赖网络和界面的纯逻辑模块：

- 输入原文、旧内容和新内容，输出新文及匹配次数。
- 使用固定文字匹配，不解释正则表达式或 Markdown 语法。
- 旧内容为空时拒绝执行。
- 旧内容与新内容相同时不产生提交。
- 未找到匹配时返回“跳过”。
- 保留未匹配内容、原始换行和 UTF-8 BOM，不做全文件格式化。
- 非 UTF-8 或无法安全解码的文件标记为失败，不进行猜测性转换。

### 3.4 平台适配器

定义统一接口，使后续平台接入不影响界面和替换核心：

- `list_repositories()`：分页返回仓库标识、完整名称、默认分支和网页地址。
- `read_readme(repository)`：返回默认分支根目录 `README.md` 的内容、文件 SHA 和分支名。
- `update_readme(repository, snapshot, new_content, message)`：使用预览时的 SHA 更新文件，返回提交标识和提交链接。

第一版实现 Gitee 适配器。GitHub 和 GitCode 后续分别新增适配器，不在第一版中创建空壳实现。

### 3.5 凭据存储

- 用户不使用账号密码登录，使用 Gitee 私人访问令牌。
- 令牌默认只保存在当前进程内存中，退出后清除。
- 用户主动选择“记住令牌”时，使用 Windows 凭据管理器保存。
- 令牌不写入源码、配置、任务报告或日志，不显示在界面错误信息中。
- 令牌仅发送到 Gitee 官方接口，不发送到其他服务。

### 3.6 任务报告

每批任务生成不含敏感信息的本地 JSON 报告，记录：

- 任务时间和统一提交说明。
- 仓库完整名称、默认分支和任务状态。
- 匹配次数、提交标识和提交链接。
- 可展示的错误类别与重试结果。

报告不记录访问令牌、完整 README 内容或新旧替换文本。

## 4. Gitee 接口设计

使用 Gitee API v5：

- 列出仓库：`GET /api/v5/user/repos`，按页读取，`per_page` 最大为 100，直到取得全部页面。
- 读取文件：`GET /api/v5/repos/{owner}/{repo}/contents/README.md`，指定仓库默认分支，保存返回内容和文件 Blob SHA。
- 更新文件：`PUT /api/v5/repos/{owner}/{repo}/contents/README.md`，提交 Base64 编码的新内容、统一提交说明、默认分支和预览时取得的 SHA。

读取与更新使用相同的仓库、分支和路径。接口路径参数必须正确转义，文件内容按 API 要求编码，不能将 Base64 文本当作 README 正文展示。

官方参考：[Gitee API 文档](https://gitee.com/api/v5/swagger)。

## 5. 核心数据与状态

### 仓库

- 平台标识。
- 所有者路径和仓库路径。
- 完整名称。
- 默认分支。
- 仓库网页地址。

### 文件快照

- 路径，固定为 `README.md`。
- 分支，固定为该仓库默认分支。
- 原始文本。
- 文件 Blob SHA。

### 预览项

- 仓库和文件快照。
- 新文本。
- 匹配次数。
- 统一差异文本。
- 状态：`待提交`、`无匹配`、`无变化`、`读取失败`。
- 可展示错误信息。

### 提交结果

- 状态：`成功`、`失败`、`冲突`。
- 提交标识和提交链接。
- 错误类别及是否允许重试。

## 6. 使用流程与安全约束

1. 用户输入令牌并加载仓库。
2. 用户勾选仓库，输入旧内容、新内容和提交说明。
3. 工具校验：至少选择一个仓库，旧内容非空，提交说明非空。
4. 用户点击“生成预览”。此阶段只调用读取接口，不调用更新接口。
5. 工具逐仓库生成结果；有实际变化的项进入“待提交”，无匹配或无变化项不可提交。
6. 用户展开检查差异，点击“确认提交”。
7. 工具显示待提交仓库数及替换总次数，用户再次确认。
8. 工具仅提交有效的“待提交”项，每个仓库产生一次独立提交。
9. 页面展示结果并保存任务报告；可恢复失败可单仓库重试。

提交必须使用预览时的文件 SHA。如果远端文件已变化，Gitee 拒绝更新，工具将该项标记为“冲突”，要求重新读取和预览，不能自动使用新 SHA 强制覆盖。

预览生成后，只要仓库选择、旧内容、新内容或提交说明变化，就必须重新预览。提交成功的项从待提交集合移除，避免重复提交。

## 7. 异常处理

| 情况 | 行为 | 是否可重试 |
| --- | --- | --- |
| 无匹配或替换后无变化 | 跳过，不产生提交 | 无需重试 |
| README 不存在 | 标记跳过及原因，不创建文件 | 无需重试 |
| 文件不是 UTF-8 或内容无法安全处理 | 当前仓库失败 | 修改文件后重新预览 |
| 令牌无效或过期 | 停止新的请求并提示重新认证 | 更新令牌后重试 |
| 仓库权限不足 | 当前仓库失败，其他仓库继续 | 权限修复后重试 |
| 网络超时或临时服务错误 | 有次数上限的退避重试 | 可手动重试 |
| 接口限流 | 按限流信息等待，降低并发 | 可手动重试 |
| 文件 SHA 冲突 | 标记冲突，不覆盖远端内容 | 必须重新预览 |
| 部分仓库提交成功 | 保留成功结果，继续其他仓库 | 仅重试失败项 |

界面错误信息用于定位问题，但不泄露令牌。任务协调器不得将失败仓库的新 SHA 自动用于同一批提交。

## 8. 界面状态

主界面按顺序分为四个区域：

1. **连接与仓库**：令牌、加载状态、仓库列表、勾选状态。
2. **替换规则**：旧内容、新内容、提交说明。
3. **修改预览**：仓库状态、匹配次数、差异和待提交总数。
4. **执行结果**：进度、成功链接、失败原因和重试操作。

读取、预览和提交期间禁用会造成状态不一致的输入控件。提交按钮只在存在有效待提交项时可用。

## 9. 验证方案

### 单元测试

替换核心覆盖：

- 单处和多处匹配。
- 中文、多行、Markdown 特殊字符。
- 大小写不同不视为匹配。
- 空旧内容被拒绝，空新内容可删除匹配文本。
- 无匹配、旧新内容相同。
- CRLF/LF 换行和 UTF-8 BOM 保持不变。

平台适配器使用模拟 HTTP 响应覆盖：

- 仓库分页和默认分支提取。
- README 内容解码、更新内容编码。
- 读取和更新参数中的仓库、分支、路径与 SHA。
- 认证失败、权限不足、限流、临时错误和 SHA 冲突。
- 日志及异常信息不包含令牌。

任务协调器覆盖：

- 单仓库失败不影响其他仓库。
- 无匹配及无变化项不进入提交。
- 输入变化使预览失效。
- 只有有效预览可以提交。
- 成功项不会重复提交，失败项可独立重试。

### 真实端到端验证

使用专门的 Gitee 测试仓库，不使用用户的正式项目：

1. 加载仓库并勾选测试仓库。
2. 替换 README 中的指定内容并检查差异。
3. 确认提交，打开提交链接核对远端内容。
4. 验证无匹配跳过和失败重试。
5. 在预览后通过网页修改 README，验证工具检测 SHA 冲突且不会覆盖网页修改。

真实验证使用的令牌不得写入测试代码、 fixtures、日志或报告。

## 10. 验收标准

- 用户无需克隆仓库即可完成整个批量修改流程。
- 所有远端修改之前均有逐仓库差异预览和二次确认。
- 工具只修改选中仓库默认分支根目录的 `README.md`。
- 无匹配、无变化和缺失 README 的仓库不会产生提交。
- 每个实际变化的仓库只产生一次提交，结果可点击核对。
- 远端文件在预览后变化时不会覆盖新内容。
- 单个仓库失败不影响其他仓库，可单独重试失败项。
- 令牌不出现在文件、日志、错误信息和任务报告中。
- 自动化测试及真实测试仓库的端到端流程通过。

## 11. 后续扩展

新增 GitHub 或 GitCode 时，实现相同平台适配接口，并补充该平台的认证、分页、文件 SHA/版本机制和错误映射。替换核心、预览模型、提交安全约束和大部分界面保持不变。后续需求如章节替换、正则替换或 Pull Request，应作为独立功能重新评估，不纳入第一版隐式扩展。
